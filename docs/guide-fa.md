# راهنمای فارسی فیل‌اسلایس (FailSlice)

> وضعیت این سند: به‌روز تا پایان مرحلهٔ ۳ (ابزار خط فرمان، گزارش، مانیفست و تست pytest تولیدی). این راهنما با تکمیل هر مرحلهٔ پروژه به‌روز می‌شود؛ تاریخچهٔ تغییراتش در انتهای سند آمده است.

## فیل‌اسلایس چیست؟

فیل‌اسلایس ابزاری متن‌باز برای کوچک‌کردن «بازتولید باگ داده» است. وقتی یک کوئری یا پایپ‌لاین داده روی هزاران یا میلیون‌ها ردیف در چند جدول خراب می‌شود، معمولاً فقط چند ردیف مقصرند. فیل‌اسلایس آن چند ردیف را پیدا می‌کند و در این مسیر:

- کلیدهای خارجی بین جدول‌ها را سالم نگه می‌دارد (هیچ ارجاع معلق تازه‌ای نمی‌سازد)
- فقط پیکربندی‌هایی را می‌پذیرد که خطا روی آن‌ها واقعاً دیده شده است
- نتیجه را در یک پردازهٔ تازهٔ پایتون و فقط از روی فایل‌های خروجی دوباره اجرا و تأیید می‌کند
- برچسب نتیجه را صادقانه می‌زند: «کوچک‌شده» یا «1-minimal (verified)»
- یک گزارش خوانا، یک مانیفست با هش همهٔ فایل‌ها و یک تست رگرسیون pytest آماده تحویل می‌دهد که فقط به `pytest` و `duckdb` نیاز دارد

فیل‌اسلایس علت ریشه‌ای باگ را پیدا نمی‌کند و ادعای کوچک‌ترین نتیجهٔ ممکن را هم ندارد؛ کارش جداکردن ردیف‌های لازم است تا انسان یا عامل هوش مصنوعی راحت‌تر علت را بفهمد.

## کار ویژهٔ فیل‌اسلایس چیست؟

هیچ‌کدام از ایده‌های پایهٔ فیل‌اسلایس تازه نیست: delta debugging (الگوریتم ddmin) روشی شناخته‌شده برای کوچک‌کردن ورودی خراب است و ابزارهای زیرمجموعه‌سازی پایگاه داده هم سال‌هاست نمونه‌های سازگار با کلید خارجی می‌سازند. کار ویژهٔ فیل‌اسلایس ترکیب این دو برای مسئله‌ای است که ابزارهای رایج پاسخ نمی‌دهند:

- **لاگ و مانیتورینگ** می‌گویند کدام job یا مرحله خراب شد، ولی داده‌ای که خرابی را ساخته هنوز میلیون‌ها ردیف است.
- **ابزارهای کیفیت داده** ردیف‌هایی را پیدا می‌کنند که یک قاعدهٔ ردیفی را نقض می‌کنند. اما سخت‌ترین باگ‌ها از «ترکیب» چند ردیف در چند جدول ساخته می‌شوند: کلید تکراری به‌اضافهٔ joinی که جمع را دوبرابر می‌کند، NULL داخل زیرکوئری `NOT IN`، یا تساوی زمان در منطق «آخرین رکورد هر کلید». در این حالت هیچ ردیفی به‌تنهایی غلط نیست که ابزار نشانش دهد.
- **کوچک‌کننده‌های کلاسیک** متن یا کد را کوچک می‌کنند و از رابطهٔ بین جدول‌ها خبر ندارند؛ حذف دستی ردیف‌ها هم کلیدهای خارجی را می‌شکند و باگ را عوض می‌کند.
- **ابزارهای زیرمجموعه‌سازی** کلیدهای خارجی را سالم نگه می‌دارند، ولی ردیف‌ها را با نمونه‌گیری یا قاعده انتخاب می‌کنند، نه بر اساس اینکه باگ هنوز هست یا نه.

پرسش فیل‌اسلایس این است: «کوچک‌ترین تکه از این جدول‌ها که هنوز همین خطا را می‌سازد چیست؟» و پاسخش این ویژگی‌ها را دارد:

- جست‌وجو با **گزارهٔ خطای شما** هدایت می‌شود، نه با یک قاعدهٔ عمومی.
- هر پیکربندی‌ای که گزاره می‌بیند **از نظر کلید خارجی سالم** است؛ پس باگی که می‌ماند محصول دادهٔ واقعی است، نه ارجاع‌های شکسته.
- ادعاها **بررسی می‌شوند، نه فرض**: نتیجه در پردازهٔ جدا و فقط از فایل‌های خروجی دوباره اجرا می‌شود و برچسب «1-minimal (verified)» فقط وقتی داده می‌شود که این بررسی واقعاً انجام شده باشد.
- خروجی **قابل‌استفاده** است: یک تست pytest مستقل که امروز باگ را مستند می‌کند و بعد از اصلاح جلوی برگشتنش را می‌گیرد.
- در مرحلهٔ ۴، **سرور MCP** اضافه می‌شود تا یک عامل هوش مصنوعی بدون ریختن میلیون‌ها ردیف در context خودش، از «این فایل‌های من» به «این تست شکست‌خورده» برسد.

فیل‌اسلایس ردیف‌ها را جدا می‌کند؛ علت ریشه‌ای را تعیین نمی‌کند و ادعا نمی‌کند که بازتولید کوچک‌تری وجود ندارد.

## مفاهیم کلیدی

- **گزارهٔ خطا** (predicate): یک کوئری `SELECT` در DuckDB که می‌گوید «باگ وجود دارد». هر بار اجرا یکی از چهار نتیجهٔ `TRUE`، `FALSE`، `ERROR` یا `TIMEOUT` را می‌گیرد و فقط `TRUE` یعنی «هنوز خراب است».
- **پیکربندی** (configuration): مجموعه‌ای از ردیف‌های نگه‌داشته‌شده در هر جدول.
- **کلید خارجی** (foreign key): رابطه‌ای به شکل `child.col -> parent.col` بین دو جدول. مقدار NULL یعنی «ارجاعی وجود ندارد».
- **یتیم ورودی** (input orphan): ردیفی که از همان ابتدا در دادهٔ ورودی به والدِ ناموجود اشاره می‌کند. فیل‌اسلایس این ردیف‌ها را «تعمیر» نمی‌کند و فقط به‌عنوان استثنای ثبت‌شده نگه می‌دارد، چون گاهی خودِ باگ همین است.
- **حذف آبشاری** (cascade): با حذف یک ردیف والد، ردیف‌های فرزندی که والدشان را از دست می‌دهند هم حذف می‌شوند تا داده سالم بماند.
- **کمینگی ۱** (1-minimality): نتیجه وقتی «1-minimal» است که حذف هر ردیف تکیِ باقی‌مانده (با قاعدهٔ آبشاری) گزاره را FALSE کند. این برچسب فقط وقتی داده می‌شود که این بررسی واقعاً تا آخر اجرا شده باشد.
- **اجرای مجدد مستقل** (replay): ساختن یک پایگاه دادهٔ تازه فقط از فایل‌های خروجی در یک پردازهٔ جدا و اجرای دوبارهٔ گزاره و بررسی کلیدهای خارجی.

## نصب

پروژه هنوز روی PyPI منتشر نشده است و فعلاً از سورس نصب می‌شود. پیش‌نیازها پایتون ۳٫۱۱ یا بالاتر و ابزار [uv](https://docs.astral.sh/uv/) هستند.

```bash
git clone https://github.com/sdmhdn/failslice.git
cd failslice
uv sync
```

## اولین اجرا با نمونهٔ آماده

در پوشهٔ `examples/quickstart` یک نمونهٔ کامل هست: ۱٬۰۰۰ مشتری، ۵٬۰۰۱ سفارش و ۲۰٬۰۰۰ قلم سفارش، که سفارش شمارهٔ ۴۲۴۲ در آن دو بار بارگذاری شده و جمع درآمد را در join زیاد نشان می‌دهد.

```bash
cd examples/quickstart
uv run python make_data.py   # ساخت داده در data/generated
uv run failslice check
uv run failslice reduce
```

خروجی دستور `reduce` (شناسهٔ اجرا و مسیرها در سیستم شما فرق می‌کند):

```text
1-minimal (verified): 26,001 -> 4 rows (0.02%); replay verified
run directory: .../examples/quickstart/.failslice/runs/<run-id>
  report: .../report.md
  test:   pytest .../pytest
```

یعنی از ۲۶٬۰۰۱ ردیف فقط ۴ ردیف ماند: یک مشتری، همان سفارش تکراری (دو بار) و یک قلم سفارش. این اعداد را تست `tests/test_examples.py` بررسی می‌کند.

گام‌های بعدی:

```bash
uv run failslice explain .failslice/runs/<run-id>     # مشاهده‌ها دربارهٔ ردیف‌های باقی‌مانده
uv run pytest .failslice/runs/<run-id>/pytest         # اجرای تست تولیدی
uv run failslice export-test .failslice/runs/<run-id> --out tests/data_bug_4242
```

خروجی `explain` در این نمونه نشان می‌دهد که کلید ۴۲۴۲ در جدول سفارش‌ها دو ردیف والد دارد و join اعلام‌شده برای آن دو جفت تولید می‌کند. این فقط یک مشاهده است، نه تشخیص علت.

## شروع با دادهٔ خودتان

دستور `init` یک فایل پیکربندی اولیه از روی یک پوشه از فایل‌های CSV و Parquet می‌سازد:

```bash
uv run failslice init path/to/data
```

- همهٔ جدول‌ها با مسیرشان فعال نوشته می‌شوند.
- کلیدهای اصلی و خارجی فقط به‌صورت **پیشنهاد** و کامنت‌شده نوشته می‌شوند، همراه با سطح اطمینان (`high`، `medium` یا `low`) و شواهد (تعداد ردیف‌های بررسی‌شده، مقدارهای تکراری یا NULL، تعداد مقدارهای منطبق). بعد از بررسی، کامنت هر کدام را که درست است بردارید.
- کلید والدِ تکراری هم پیشنهاد می‌شود و تکرارش صریحاً گفته می‌شود، چون کلید تکراری اغلب خودِ باگ است.
- به‌طور پیش‌فرض فقط ۱۰٬۰۰۰ ردیف اول هر فایل خوانده می‌شود؛ برای بررسی کامل از `--full-scan` استفاده کنید. پیشنهادهای مبتنی بر نمونه همیشه سطح `low` دارند.
- گزاره با `SELECT false` جایگذاری می‌شود که باید آن را با گزارهٔ واقعی عوض کنید؛ تا آن موقع دستور `check` خطای «گزاره هیچ‌وقت TRUE نیست» می‌دهد.
- فایل موجود هرگز بازنویسی نمی‌شود.

## نوشتن فایل پیکربندی

فایل پیکربندی `failslice.yaml` نام دارد و مسیرهای داخل آن نسبت به پوشهٔ خود فایل سنجیده می‌شوند.

```yaml
version: 1
tables:
  customers: { path: data/customers.csv, primary_key: id }
  orders:    { path: data/orders.parquet, primary_key: order_id }
  lines:     { path: data/lines.parquet }
foreign_keys:
  - orders.customer_id -> customers.id
  - lines.order_id -> orders.order_id
predicate:
  sql: |
    SELECT (SELECT sum(l.amount) FROM lines l JOIN orders o USING (order_id))
        <> (SELECT sum(amount) FROM lines)
settings: { seed: 0, max_evals: 5000, wall_clock_s: 300 }
```

### بخش جدول‌ها

- کلید `path`: مسیر فایل CSV، Parquet یا `.duckdb`. مسیر باید داخل «ریشهٔ مجاز» بماند (به‌طور پیش‌فرض پوشهٔ فایل پیکربندی) و نباید کاراکترهای glob یعنی `* ? [ ] { }` داشته باشد.
- کلید `format`: یکی از `csv`، `parquet` یا `duckdb`؛ اگر ننویسید از پسوند فایل حدس زده می‌شود.
- کلید `source_table`: نام جدول داخل فایل `.duckdb` (پیش‌فرض همان نام تعریف‌شده). فقط جدول فیزیکی پذیرفته می‌شود، نه view.
- کلید `primary_key`: فقط برای اطلاع است و هرگز اعمال نمی‌شود، چون کلید تکراری اغلب خودِ باگ است.

### بخش کلیدهای خارجی

- هر کلید خارجی تک‌ستونی و به شکل `child.col -> parent.col` است.
- گراف کلیدها باید بدون چرخه باشد؛ ارجاع جدول به خودش هم چرخه حساب می‌شود و پذیرفته نیست.
- ستون والد لازم نیست یکتا باشد؛ ارجاع با مقدار سنجیده می‌شود.

### بخش تنظیمات

- کلید `seed`: ترتیب جست‌وجو را تعیین می‌کند؛ seed یکسان نتیجهٔ یکسان می‌دهد (برای اجراهایی که با محدودیت زمانی متوقف نشده‌اند).
- کلید `max_evals`: بیشترین تعداد اجرای گزاره (پیش‌فرض ۵۰۰۰). نتیجه‌های برگرفته از حافظهٔ نهان حساب نمی‌شوند.
- کلید `wall_clock_s`: بودجهٔ زمانی کل اجرا به ثانیه (پیش‌فرض ۹۰۰)، شامل خروجی‌گرفتن و اجرای مجدد.
- کلید `eval_timeout_s`: سقف زمان یک اجرای گزاره (پیش‌فرض ۳۰ ثانیه).
- کلید `minimality`: اجرای مرحلهٔ گواهی کمینگی (پیش‌فرض `true`).
- کلید `allow_nondeterministic`: اگر گزاره روی کل داده ناپایدار باشد، به‌جای توقف ادامه می‌دهد ولی هیچ ادعای کمینگی نمی‌کند (پیش‌فرض `false`).
- کلید `threads`: تعداد threadهای DuckDB (پیش‌فرض ۱، برای تکرارپذیری).

## نوشتن گزاره

گزاره دقیقاً یک `SELECT` فقط‌خواندنی است (CTE مجاز است) و فقط از نام جدول‌های تعریف‌شده استفاده می‌کند. سه شکل دارد.

### شکل بولی

نتیجه باید دقیقاً یک ردیف و یک ستون BOOLEAN باشد. مقدار TRUE یعنی باگ هست و FALSE یا NULL یعنی نیست.

```yaml
predicate:
  sql: SELECT count(*) > 0 FROM orders WHERE customer_id IS NULL
```

### شکل انتظار

باگ وقتی وجود دارد که نتیجهٔ کوئری با مقدار مورد انتظار فرق کند (یا با `mode: equals` وقتی برابر باشد).

```yaml
predicate:
  expect:
    query: SELECT coalesce(sum(amount), 0) - coalesce(sum(paid), 0) FROM lines
    expected: 0               # یا expected_file: expected.csv
    mode: differs             # differs یا equals
    ordered: false            # پیش‌فرض: ترتیب ردیف‌ها مهم نیست
    float_tolerance: 0.001    # اختیاری
```

قواعد مقایسه:

- مقایسه دقیق و نوع‌دار است: عدد صحیح و اعشاری هیچ‌وقت از مسیر float گرد نمی‌شوند، مقدار بولی با عدد برابر نیست (حتی داخل لیست یا MAP) و NULL با NULL برابر است.
- انتظار تک‌مقداری (مثل `expected: 0` یا حتی `expected: null`) نتیجهٔ ۱×۱ می‌خواهد.
- اگر مقایسه به هر دلیلی ممکن نباشد، نتیجه `ERROR` است و هرگز `TRUE` نمی‌شود.
- نکتهٔ مهم: با `mode: differs` جدول خالی‌شده هم معمولاً «متفاوت» است و جست‌وجو ممکن است به داده‌ای بی‌معنی برسد. کوئری‌ای بنویسید که مقدار درستش به حجم داده بستگی نداشته باشد، مثل اختلاف دو جمع که باید صفر باشد.

### شکل خطا

باگ وقتی وجود دارد که کوئری خطای DuckDB بدهد و پیامش با عبارت منظم `match` بخواند.

```yaml
predicate:
  raises:
    query: SELECT sum(CAST(raw AS INTEGER)) FROM readings
    match: Could not convert string
    error_class: ConversionException   # اختیاری
```

عبارت منظم را تا حد ممکن دقیق بنویسید؛ عبارت خیلی کلی ممکن است اجازه دهد جست‌وجو به خطای دیگری برسد که با آن هم می‌خواند.

### آنچه در گزاره ممنوع است

- هر چیزی غیر از یک `SELECT`: دستورهای DDL و DML، `COPY`، `ATTACH`، `INSTALL`، `LOAD`، `PRAGMA` و `SET`
- تابع‌های جدولی و تابع‌های خواندن فایل مثل `read_csv` و `read_parquet`
- ارجاع به جدولی غیر از جدول‌های تعریف‌شده یا CTEها، و نام‌های دارای schema
- تابع‌های ناپایدار مثل `random()`، `now()` و `uuid()`؛ فهرست کامل از کاتالوگ خود DuckDB ساخته می‌شود

## ابزار خط فرمان

- دستور `failslice init [DIR]`: ساخت فایل پیکربندی با پیشنهاد کلیدها
- دستور `failslice check`: اعتبارسنجی پیکربندی و گزاره، شمارش یتیم‌ها و بررسی پایداری
- دستور `failslice reduce`: کوچک‌سازی، خروجی، اجرای مجدد و ساخت گزارش، مانیفست، CSV و تست
- دستور `failslice verify RUN_DIR`: اجرای مجدد یک پوشهٔ اجرا در پردازهٔ تازه
- دستور `failslice export-test RUN_DIR --out DIR`: تأیید دوباره و نوشتن بستهٔ تست در پوشهٔ تازه
- دستور `failslice explain RUN_DIR`: مشاهده‌ها دربارهٔ ردیف‌های باقی‌مانده

گزینه‌های مهم:

- گزینهٔ `-c` یا `--config`: مسیر فایل پیکربندی (پیش‌فرض `failslice.yaml` در پوشهٔ فعلی)
- گزینهٔ `--root`: ریشهٔ مجاز مسیرها (پیش‌فرض پوشهٔ فایل پیکربندی)
- گزینه‌های `--seed`، `--max-evals`، `--wall-clock`، `--eval-timeout`، `--no-minimality` و `--allow-nondeterministic` در `reduce`: تغییر تنظیمات بدون ویرایش فایل
- گزینهٔ `--out` در `reduce`: پوشهٔ اجرا (باید داخل ریشهٔ مجاز باشد)
- گزینهٔ `--no-isolate`: اجرای `check` و `reduce` در همان پردازه (به‌طور پیش‌فرض در پردازهٔ جدا با مهلت سخت اجرا می‌شوند)
- گزینهٔ `--json`: چاپ دقیقاً یک سند JSON روی خروجی استاندارد، مناسب اسکریپت‌ها و عامل‌های هوش مصنوعی
- گزینهٔ `--debug`: نمایش traceback کامل خطاها

کدهای خروج (قرارداد ثابت برای اسکریپت‌ها):

- کد ۰: عملیات موفق بود (مثلاً بازتولید تأییدشده)
- کد ۱: یک شرط برقرار نشد (گزاره روی کل داده TRUE نیست، ناپایدار است، یا اجرای مجدد رد شد)
- کد ۲: ورودی، پیکربندی یا گزارهٔ نامعتبر (مثلاً مسیر بیرون از ریشه یا گزارهٔ ناامن)
- کد ۳: نتیجه‌نگرفتن به‌خاطر بودجه یا مهلت
- کد ۴: خطای اجرایی یا خطا در ساخت خروجی‌ها
- کد ۱۳۰: قطع توسط کاربر (Ctrl-C)؛ پردازهٔ فرزند متوقف می‌شود و checkpoint می‌ماند

## اجرا از پایتون

همین چرخه به‌صورت کتابخانه هم در دسترس است (فایل `examples/quickstart/run.py`).

```python
import failslice


def main() -> None:
    project = failslice.load_project("failslice.yaml")

    report = failslice.check(project)
    print(report.ok, report.orphans, report.problems)

    project = project.with_settings(seed=1, max_evals=2000)  # تغییر تنظیمات بدون ویرایش فایل
    result = failslice.reduce(project, isolate=True, on_progress=print)
    print(result.status, result.minimality_label, result.verification)


if __name__ == "__main__":
    main()
```

نکته‌ها:

- تابع `check` گزاره را اعتبارسنجی می‌کند، یتیم‌های ورودی را می‌شمارد و گزاره را چهار بار روی کل داده اجرا می‌کند تا پایداری‌اش سنجیده شود. با `isolate=True` این کار در پردازهٔ جدا انجام می‌شود.
- با `isolate=True` کوچک‌سازی در یک پردازهٔ فرزند با مهلت سخت اجرا می‌شود. در این حالت محافظ `if __name__ == "__main__":` لازم است.
- بدون `isolate=True` مهلت‌ها همکارانه‌اند: کوئری SQL قطع می‌شود ولی کار سمت پایتون (مثلاً یک عبارت منظم کند) نه.
- تابع `on_progress` در حالت ایزوله روی thread جدا اجرا می‌شود و فقط آخرین رویداد را می‌گیرد؛ آن را سبک و غیرمسدودکننده نگه دارید.
- تابع `failslice.verify(run_dir)` یک پوشهٔ اجرای قبلی را دوباره در پردازهٔ تازه تأیید می‌کند.

## خواندن نتیجه

- مقدار `result.status` برابر `reduced` است اگر پیکربندی تأییدشده‌ای خروجی گرفته شد، و `no-candidate` اگر اجرا پیش از تأیید هر پیکربندی متوقف شد (آمار در هر دو حالت در `result.stats` هست).
- مقدار `result.minimality_label` یکی از `1-minimal (verified)`، `reduced, minimality not verified` یا `no reproducer` است.
- مقدار `result.verification.status` یکی از این‌هاست:
  - حالت `verified`: گزاره در اجرای مجدد TRUE بود و کلیدهای خارجی سالم‌اند
  - حالت `replay-failed`: گزاره در اجرای مجدد TRUE نشد (معمولاً وابستگی به ترتیب یا تغییر نوع داده)
  - حالت `integrity-failed`: ارجاع معلق تازه یا فرادادهٔ یتیم‌های خراب پیدا شد
  - حالت `unverified`: زمان کافی برای اجرای مجدد نماند
- فهرست `result.notes` هشدارها را نشان می‌دهد، مثلاً وقتی نوعی از داده در Parquet قابل بازگرداندن نبوده است.
- شیء `result.spec` قرارداد نوع‌دار خروجی (`spec.json`) است.
- شیء `result.manifest` خلاصهٔ مرجع اجرا (`manifest.json`) است؛ تابع `failslice.artifacts.load_manifest(run_dir)` آن را از دیسک می‌خواند.
- برچسب `1-minimal (verified)` فقط وقتی داده می‌شود که گواهی کمینگی کامل شده، اجرای مجدد تأیید شده و خروجی بدون اتلاف بوده باشد.

## پوشهٔ خروجی

هر اجرا یک پوشه می‌سازد (پیش‌فرض `.failslice/runs/<run-id>/` کنار فایل پیکربندی):

- فایل `report.md`: خلاصهٔ خوانا (نتیجه، تعداد ردیف‌ها، گزاره، کلیدهای خارجی، مشاهده‌ها، آمار جست‌وجو، یادداشت‌ها و راه بازتولید)
- فایل `manifest.json`: خلاصهٔ مرجع (نسخه‌ها، تنظیمات، هش ورودی‌ها، تعداد ردیف و اسکیمای هر جدول، آمار، نتیجهٔ اجرای مجدد، وضعیت هر مرحلهٔ پایانی و فهرست همهٔ فایل‌ها با اندازه و هش). مقدارهای نامعلوم `null` می‌مانند و هرگز حدس زده نمی‌شوند.
- پوشهٔ `tables/`: ردیف‌های نگه‌داشته‌شدهٔ هر جدول به‌صورت Parquet و به ترتیب اصلی (منبع اصلی)
- پوشهٔ `csv/`: نسخهٔ CSV برای راحتی؛ سطر عنوان دارد، NULL به‌صورت `\N` بدون کوتیشن و متن‌ها داخل کوتیشن نوشته می‌شوند؛ نوع داده‌ها حفظ نمی‌شود
- پوشهٔ `pytest/`: بستهٔ تست تولیدی (فقط اگر اجرای مجدد تأیید شده باشد)
- فایل `explain.json`: مشاهده‌ها دربارهٔ ردیف‌های باقی‌مانده
- فایل `spec.json`: قرارداد نوع‌دار و نسخه‌دار بازتولید (نسخهٔ ۳)
- فایل `rowmap.parquet`: شمارهٔ هر ردیف خروجی در فایل ورودی
- فایل `orphans.parquet`: یتیم‌های ورودی باقی‌مانده
- فایل `expected/expected.parquet`: نسخهٔ ثابت فایل انتظار، اگر استفاده شده باشد
- فایل `checkpoint.json`: آخرین پیکربندی تأییدشده و آمار آن، برای بازیابی اجرایی که متوقف شده

اگر بودجهٔ زمانی پیش از ساخت همهٔ خروجی‌ها تمام شود، گزارش و مانیفست همیشه نوشته می‌شوند و مرحله‌های جامانده در بخش «Incomplete steps» گزارش و فیلد `steps` مانیفست ثبت می‌شوند.

## تست تولیدی

بستهٔ تست (در `pytest/` یا هر پوشه‌ای که با `export-test --out` بدهید) این فایل‌ها را دارد:

- فایل `test_<name>.py`: خود تست؛ نوع انتظار در ثابت `EXPECT` در بالای فایل نوشته شده است. نام پیش‌فرض `reproducer_<hash>` است (هش داده‌ها و نوع انتظار) تا چند بسته کنار هم در یک اجرای pytest تداخل نکنند؛ با `--name` می‌توانید نام دیگری بدهید
- فایل `query.sql`: کوئری گزاره؛ پس از اصلاح پایپ‌لاین آن را ویرایش کنید
- فایل `reproducer.json`: شکل و پارامترهای گزاره، اسکیماها، کلیدهای خارجی و هش داده‌ها
- پوشهٔ `fixtures/`: جدول‌های کوچک‌شده (در `fixtures/tables/`) و یتیم‌های مجاز (`fixtures/orphans.parquet`)
- فایل `_failslice_portable.py`: کپی دقیق ماژولی که خود فیل‌اسلایس با آن نتیجه را طبقه‌بندی می‌کند

نکته‌ها:

- تست فقط به `pytest` و `duckdb` نیاز دارد، مسیر مطلق ندارد و دادهٔ اصلی شما را نمی‌خواند؛ می‌توانید پوشه را هر جایی از مخزن خودتان کپی کنید.
- پیش از اجرای گزاره، هش داده‌ها، اسکیما و سلامت کلیدهای خارجی بررسی می‌شود؛ تغییر دادن داده‌ها تست را رد می‌کند.
- حالت `--expect fails` (پیش‌فرض) یعنی تست تا وقتی باگ وجود دارد پاس می‌شود؛ مناسب مستندکردن باگ.
- حالت `--expect passes` یعنی تست وقتی پاس می‌شود که باگ برطرف شده باشد. پس از اصلاح پایپ‌لاین، SQL اصلاح‌شده را در `query.sql` بگذارید.
- هر نتیجهٔ دیگر (خطای نامرتبط، نتیجهٔ نادرست یا تمام‌شدن مهلت) در هر دو حالت تست را رد می‌کند.
- چند بستهٔ تست را می‌شود هم‌زمان در یک اجرای pytest داشت، به شرط آن‌که نام فایل‌های تست فرق کند (نام پیش‌فرض این را تضمین می‌کند، مگر این‌که یک اجرا را با همان نوع انتظار دو بار خروجی بگیرید)؛ هر بسته کپی خودش از ماژول را جداگانه بارگذاری می‌کند.

## تضمین‌ها و محدودیت‌ها

تضمین‌ها (هر کدام در کد اعمال و با تست پوشش داده شده‌اند):

- پیکربندی فقط پس از یک ارزیابی تازه با نتیجهٔ TRUE پذیرفته می‌شود؛ حافظهٔ نهان فقط نتیجه‌های منفی را نگه می‌دارد.
- هیچ ارجاع معلق تازه‌ای ساخته نمی‌شود و یتیم‌های ورودی به‌عنوان استثنا باقی می‌مانند.
- نتیجه در پردازهٔ تازه و فقط از فایل‌های خروجی دوباره اجرا می‌شود؛ نوع‌هایی مثل ENUM که Parquet ندارد پیش از اجرای گزاره بازگردانده می‌شوند.
- برچسب `1-minimal (verified)` فقط پس از کامل‌شدن مرحلهٔ گواهی داده می‌شود.
- ورودی، تنظیمات و seed یکسان نتیجهٔ یکسان می‌دهند، به شرط آن‌که اجرا با محدودیت زمانی متوقف نشده باشد و هیچ ارزیابی‌ای به مهلت (`TIMEOUT`) نخورده باشد؛ رویدادهای زمانی به بار سیستم وابسته‌اند و در گزارش ثبت می‌شوند.
- از هر فایل ورودی قبل و بعد از بارگذاری هش گرفته می‌شود؛ فایلی که حین بارگذاری عوض شود رد می‌شود.

محدودیت‌ها:

- فقط کلید خارجی تک‌ستونی و بدون چرخه پشتیبانی می‌شود.
- همهٔ داده در حافظه بارگذاری می‌شود.
- مشاهده‌های `explain` توصیف داده‌اند، نه تشخیص علت؛ فیل‌اسلایس نمی‌داند گزاره به کدام join یا ستون وابسته است.
- گزاره باید قطعی باشد؛ گزاره‌های ناپایدار به‌طور پیش‌فرض رد می‌شوند.

## امنیت

- همهٔ مسیرها (با دنبال‌کردن symlink) باید داخل ریشهٔ مجاز بمانند.
- گزاره پیش از اجرا با sqlglot اعتبارسنجی می‌شود.
- بعد از بارگذاری، دسترسی DuckDB به فایل‌های بیرونی خاموش می‌شود؛ این مانع اصلی است و اعتبارسنجی SQL لایهٔ دفاعی دوم است.
- در اجرای مجدد، هر مسیر و هر نوع ستونی که در `spec.json` آمده دوباره بررسی می‌شود تا یک فایل دست‌کاری‌شده نتواند فایل بیرونی بخواند یا SQL تزریق کند.

## عیب‌یابی رایج

- خطای `PredicateNotFailingError`: گزاره روی کل داده هیچ‌وقت TRUE نشد؛ یعنی چیزی برای کوچک‌کردن نیست. گزاره یا داده را بررسی کنید.
- خطای `DeterminismError`: گزاره روی کل داده نتیجهٔ یکسان نمی‌دهد. ترتیب‌وابستگی (مثلاً `LIMIT` بدون `ORDER BY`) را برطرف کنید یا آگاهانه `allow_nondeterministic` را روشن کنید.
- خطای `PredicateValidationError`: گزاره قاعده‌های امنیتی را نقض می‌کند؛ ویژگی `reason` نوع مشکل را می‌گوید.
- خطای `ConfigError`: فایل پیکربندی، مسیر یا گراف کلیدها مشکل دارد؛ پیام خطا محل دقیق را می‌گوید.
- وضعیت `no-candidate`: بودجه پیش از تأیید هر پیکربندی تمام شد؛ `max_evals` یا `wall_clock_s` را بیشتر کنید.
- وضعیت `replay-failed`: نتیجه در اجرای مجدد بازتولید نشد؛ جزئیات در `result.verification.detail`، `result.notes` و `report.md` است.
- پیام «already exists» در `init` یا `export-test`: فیل‌اسلایس فایل یا پوشهٔ موجود را بازنویسی نمی‌کند؛ مسیر دیگری بدهید.
- پیام «resolves outside the allowed root»: مسیر `--out` یا مسیرهای پیکربندی باید داخل ریشهٔ مجاز باشند؛ با `--root` ریشه را مشخص کنید.
- شکست تست تولیدی با پیام «sha256 mismatch»: داده‌های داخل `fixtures/` تغییر کرده‌اند؛ بسته را دوباره با `export-test` بسازید.
